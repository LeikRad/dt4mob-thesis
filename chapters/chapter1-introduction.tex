\section{Context and Motivation}
\label{sec:context}

A \emph{digital twin} is a virtual representation of a physical entity, kept synchronised with its real-world counterpart through a live data connection. Although the term is used inconsistently across disciplines~\cite{abdelrahman2025whatisdigitaltwin}, most definitions share three elements: a physical entity, a virtual entity that represents it, and a connection -- ideally continuous and bidirectional -- between the two. Applied to physical infrastructure, a digital twin is a realistic digital model of assets, processes, or systems in the built environment, updated to reflect the state of its physical counterpart~\cite{broo2021digitaltwins}.

In the mobility domain, the physical entities of interest are the components of a road network: the carriageway itself and its pavement, drainage, and slopes; road furniture such as signs, barriers, and kilometre markers; structures such as bridges and retaining walls; and the sensing and telematics equipment that instruments them -- weather stations, traffic cameras, variable message signs, emergency call points, and toll infrastructure. Increasingly, these are complemented by \emph{simulated} entities: vehicles produced by a traffic simulator, or the projected spread of a wildfire, which have no fixed physical counterpart but are streamed through the same channels and are expected to appear in the same scene.

A digital twin system for this domain is conventionally divided into two halves. A \emph{backend} ingests data from the physical assets and from simulators, models each entity as a structured record, and exposes those records through a common interface, typically over HTTP and a streaming protocol such as WebSocket. Eclipse Ditto~\cite{kherbache2022ditto} is one such backend. The other half is a \emph{viewer}: an interactive application that fetches those records, places each entity at its real-world geographic position on a three-dimensional globe, renders it, and updates it as new data arrives, so that an operator can see the current state of the infrastructure at a glance and inspect any individual entity.

This thesis is concerned with the viewer. The specific viewer it describes was developed in the context of the DT4MOB project, using an Eclipse Ditto deployment as its data source, but the concerns it addresses are not specific to that project or that backend.

\subsection{Why Viewers Are Built Coupled}

In practice, infrastructure digital twin viewers tend to be built as closed, purpose-specific applications. The visualisation layer is written for one infrastructure domain and wired directly to one backend. This is a reasonable default: a viewer is usually commissioned for a single deployment, the backend and its data schema are known and fixed at the start, and the fastest path to a working application is to write rendering and interaction code directly against that schema and that API.

The cost of this default appears later. The entity types the viewer can display are fixed in its rendering and interaction code, so adding a new kind of infrastructure entity -- a new sensor type, a new class of road furniture -- means editing the spawn logic, the update handling, and the rendering path, rather than describing the new type in one place. The backend is equally fixed: its authentication scheme, its pagination, and the exact shape of its update messages are assumed throughout the codebase, so the viewer cannot be pointed at a different backend, and it cannot be run or tested at all without a live instance of the one it targets. Domain-specific and backend-specific logic accumulate throughout the same components, and the application becomes progressively harder to reason about, extend, or reuse.

\section{Problem Statement}
\label{sec:problem}

The problem this thesis addresses is the absence, in existing infrastructure digital twin viewers, of a clear internal separation between three concerns that vary independently:

\begin{enumerate}
  \item \textbf{what an entity is} -- its data schema, its visual representation, the information shown when it is selected, and any behaviour it has over time;
  \item \textbf{where an entity's data comes from} -- the backend's transport, authentication, pagination, and update-message format;
  \item \textbf{everything else} -- rendering, selection and hover, the camera, coordinate placement, and the loop that decides which entities should currently be loaded.
\end{enumerate}

When the first two are not separated from the third, the viewer is tied to one infrastructure domain and one backend, cannot be developed or validated independently of that backend, and cannot be reused. The goal of this work is a viewer in which the first two concerns are each confined to a single, well-defined seam, so that the third -- the bulk of the application -- is written once against generic abstractions and does not change when a new entity type is added or the backend is replaced.

\section{Objectives and Research Questions}
\label{sec:objectives}

The objectives of this work are:

\begin{itemize}
  \item to design and implement an open-source digital twin viewer, built on Unreal Engine, capable of visualising many types of mobility-infrastructure entities without infrastructure-specific logic spreading through the codebase;
  \item to decouple the viewer's rendering, interaction, and camera systems from the data backend that feeds them, so that the backend can be replaced or mocked without touching the rest of the application;
  \item to evaluate the resulting system, both through performance benchmarks of the entity spawning and rendering path and through user testing of the application.
\end{itemize}

These objectives are framed by the following research questions:

\begin{description}
  \item[RQ1] Can a single architectural pattern support arbitrary mobility-infrastructure entity types within an Unreal Engine viewer without type-specific code in the generic spawn, update, and rendering paths?
  \item[RQ2] Can the viewer's rendering, interaction, and camera layers be made independent of the data backend, such that the backend is replaceable and the application runs without a live instance of any particular one?
  \item[RQ3] How does the viewer's entity spawning and rendering scale with entity count, and what mesh and material strategy should a high-cardinality entity type adopt to remain tractable?
  \item[RQ4] Is the resulting application usable and coherent for its intended users when exploring a concrete dataset?
\end{description}

RQ1 and RQ2 are addressed by the architecture and implementation in Chapters~\ref{chap:architecture} and~\ref{chap:implementation}; RQ3 and RQ4 by the evaluation in Chapter~\ref{chap:evaluation}.

\section{Approach}
\label{sec:approach}

The work followed an iterative development process rather than an up-front design. An initial viewer was built against a live Eclipse Ditto backend with the coupled structure described in Section~\ref{sec:context}, sufficient to render a fixed set of entity types. The generalised and decoupled architecture was then arrived at through a sequence of refactorings, each triggered by a concrete need encountered while extending the viewer: a second way of supplying credentials, an entity type that did not fit the existing spawn path, a rendering feature that only one entity type required. Chapter~\ref{chap:implementation} presents these refactorings in order, using each as a case study of where an architectural boundary was drawn and why.

The backend was treated throughout as a fixed external dependency to build against, not as an object of study: it was used to validate the viewer, and its observed behaviour -- including its failure modes -- informed the design, but its internals are out of scope.

The evaluation has two parts. Performance is assessed with a benchmark harness that spawns and renders entities in controlled quantities and records frame timing and memory, with each configuration repeated and averaged over several runs. Usability is assessed through a user study in which participants carry out representative tasks with the viewer against a real dataset.

\section{Scope and Non-Goals}
\label{sec:scope}

This thesis is about the viewer. The following are explicitly outside its scope:

\begin{itemize}
  \item \textbf{The backend.} How digital twin data should be modelled, stored, and served, and the design of Eclipse Ditto or any alternative, are the subject of other work. This document treats the backend as an interface to consume.
  \item \textbf{The data sources.} The sensors, telematics equipment, and traffic or fire simulators that produce the data are not examined here; only the records they ultimately yield through the backend.
  \item \textbf{Backend-side performance and scalability.} The benchmarks in Chapter~\ref{chap:evaluation} measure the viewer, not the backend's throughput or query latency.
  \item \textbf{Photorealism and asset authoring.} The viewer renders whatever meshes and models it is given; producing high-fidelity 3D assets for each infrastructure type is not a goal.
\end{itemize}

\section{Contributions}
\label{sec:contributions}

The main contributions of this thesis are:

\begin{itemize}
  \item an open-source digital twin viewer for mobility infrastructure, built on Unreal Engine, that is generalisable across entity types and decoupled from its data backend;
  \item an architectural pattern for achieving that generalisation and decoupling within an Unreal Engine application -- a service layer that confines all backend contact, and an entity model driven by a registration table with two escalating extension points -- documented through the concrete development decisions that produced it;
  \item a benchmark harness and a set of results characterising the performance of the entity spawning and rendering path under this architecture;
  \item a user study evaluating the viewer from the perspective of its intended users.
\end{itemize}
