\chapter{Architecture}
\label{chap:architecture}

\begin{introduction}
This chapter presents the high-level architecture of the digital twin viewer, focusing on the design choices that make it generalisable across infrastructure types and decoupled from any single data backend. It describes the components the viewer is made of, the boundaries between them, and the seams through which new entity types are added and data sources are replaced. Its implementation is the subject of Chapter~\ref{chap:implementation}.
\end{introduction}

\section{Overview}
\label{sec:arch-overview}

The viewer is structured as four layers with deliberately narrow interfaces between them, shown in Figure~\ref{fig:arch-overview}. At the bottom, a \emph{service layer} of long-lived services owns all contact with the outside world: authentication, requests to the data backend, the live event stream, secure credential storage, remote model downloads, and coordinate conversion. Above it, an \emph{entity model} turns each backend record into an entity in the scene. It is driven by a single registration table and, for any type that needs more, by one of two optional extension mechanisms that any number of entity types may use independently, rather than by per-type code scattered through the application. A \emph{geospatial placement} seam is the only place where geographic coordinates are turned into positions in the scene. Finally, a \emph{camera, interaction, and UI layer} operates on entities and the globe, and knows nothing about entity types or where their data came from.

The guiding rule is that data-backend knowledge lives only in the service layer, and infrastructure-domain knowledge lives only behind the entity model's extension points. Everything else, meaning rendering, selection, the camera, the coordinate maths, and the loop that decides which entities to load, is written against generic abstractions (an entity, an entity identifier, a latitude/longitude pair) and does not change when a new entity type is added or the backend is swapped.

\section{Service Layer}
\label{sec:service-layer}

Every external dependency is encapsulated in its own long-lived service, created when the application starts, kept alive for the whole session, and exposed to the rest of the application through a typed interface. Splitting these responsibilities across small, single-purpose services, rather than a single monolithic client, means each concern can be reasoned about, replaced, or mocked in isolation.

\subsection{Components}

The service layer is made up of seven services, which fall into three groups according to what they do for the rest of the application. Figure~\ref{fig:service-layer} shows them, how they communicate, and where the boundary with the backend lies.

Three services handle the connection to the backend. The \emph{backend connection} owns authentication, the credentials attached to each request, and access to the backend's records, including requests limited to a geographic area; requests made before authentication completes are queued and sent once it does, so the rest of the application never has to reason about login timing. The \emph{credential store} keeps the user's login details in the operating system's secure storage, so a stored login remains usable until the user logs out, while short-lived access tokens are never stored. The \emph{live-update stream} maintains the single persistent connection over which the backend pushes changes: it connects only once authentication is ready, reconnects automatically if the connection drops, and lets other components subscribe to its events instead of handling the connection themselves.

Two services connect those changes to the scene. The \emph{update router} turns each incoming message into a generic \emph{(identifier, path, value)} triple and delivers it to the entity it concerns; messages for an entity that is not currently in the scene are reported separately, so the streaming logic can decide whether to fetch and create it. The \emph{entity registry} maps identifiers to the entities currently in the scene, so any component that needs an entity asks the registry instead of searching the scene; prefix lookups make it possible, for example, to find the instruments that belong to an asset.

The last two support the scene itself. The \emph{model cache} downloads the 3D models that entities refer to, caches them on disk, and loads them at runtime, and the \emph{coordinate conversion} service turns geographic coordinates into positions in the scene, as described in Section~\ref{sec:geospatial-placement}.

\subsection{Communication Between Services}

The services communicate through events rather than direct calls wherever timing matters: the live-update stream waits for the backend connection to announce that authentication is ready instead of polling it, and the update router listens to the stream's message events. Connection settings that several services need are read from a single place, so the running application has one interpretation of that configuration rather than several that could drift apart.

\subsection{The Backend Boundary}

Nothing above the service layer knows the backend's addresses, its authentication scheme, its transport, or the format of its messages. The entity model receives parsed records and \emph{(identifier, path, value)} triples; the camera and UI receive entities and events. Replacing the backend, or substituting a mock that replays recorded traffic for offline development, is therefore a change confined to this layer.

Within that layer, the genuinely backend-specific pieces (authentication and record access, the live connection's protocol, and decoding one live-update message) sit behind their own small interfaces rather than inside the services directly (the dashed boxes in Figure~\ref{fig:service-layer}), each currently with one implementation, for Eclipse Ditto (Section~\ref{sec:impl-backend-interface}). Each service owns its implementation the same way the entity model owns an extension or a behaviour component: created once, held through a generic interface, with the owner unaware of what the owned object actually does. This is the same seam-per-axis-of-variation principle from Section~\ref{sec:design-rationale}, applied a second time inside the service layer rather than at its boundary.

\section{Entity Model and Generalisation}
\label{sec:entity-model}

The entity model concentrates generalisation across infrastructure types. A backend record is a structured document with an identifier, a set of attributes, and optionally a set of features; the viewer's job is to turn each one into an entity in the scene that renders sensibly, shows the right information when selected, and updates live. The design goal is that adding a new kind of infrastructure requires touching exactly one table and, at most, adding one small self-contained extension, never modifying the creation pipeline, the update loop, or the rendering code.

\subsection{The Generic Entity}

Every entity in the scene, regardless of type, is an instance of the same generic entity. It is created from two things: a schema describing the expected shape of the entity's data, and the raw record received from the backend, which remains the authoritative state. The entity anchors itself to its geographic position on the globe, registers with the update router to receive live changes and with the entity registry so it can be found, and shows hover and selection visually when the interaction layer reports them.

Crucially, the generic entity has no per-type branching. It does not know what a toll camera or a weather station is. Everything type-specific reaches it through the mechanisms below.

\subsection{The Registration Table}

The registration table is the one place where the application lists the entity types it knows. Each entry associates a type key, matched against the entity's identifier, with a schema for its data, a display name, an optional default 3D model, and an optional extension (below). When a new record arrives, the entity factory matches its identifier against the registered keys, with the most specific match winning, selects the corresponding schema, and creates a generic entity. An identifier that matches no key is logged for later inspection and otherwise ignored, so an unrecognised entity is a diagnostic event, not a crash or a silent drop.

\subsection{Stateless Per-Type Behaviour: Extensions}

Most types are fully described by their table entry. When a type needs behaviour the table cannot express, it registers an \emph{extension}: a single shared object per type that answers a fixed set of questions, each with a default answer matching the generic behaviour.

Some of these questions concern presentation: the badge colour and label used in entity lists and information windows, the default set of fields shown in the information panel, and the initial data sent to the backend when the user places a new instance of the type. Others concern how entities of the type are loaded and kept current: whether the type should be fetched in full rather than by geographic area, and with what filter; whether an entity may be created on demand from a live update, rather than only when its geographic area is loaded; whether to monitor the rate of live updates and warn when they stall; whether a per-entity staleness timeout should be used instead of the expiry timestamp set by the backend; and whether the entity's typed copy of its data needs refreshing on every live change, or only once when it is created. The last question is whether the type needs an optional behaviour component, described below.

Each question exists because some concrete type needed it rather than as speculative flexibility: the staleness timeout exists so that a simulated vehicle whose latest update arrives late is not removed while still active (Section~\ref{sec:impl-ttl}), and on-demand creation exists because a new vehicle can appear while the camera sits still, so only the live update stream will ever see it. The vehicle type's extension answers several of these questions differently from the defaults, among them the staleness timeout and on-demand creation. The factory always provides an extension, a shared generic default for types that registered none, so no part of the application ever has to check whether a type has custom behaviour.

\subsection{Stateful Per-Instance Behaviour: Behaviour Components}

Some types need live per-\emph{instance} state, such as fetched geometry, resolved model locations, or a simulation's current area. A shared extension cannot hold that. For these types, the extension provides a \emph{behaviour component}, and the generic entity attaches one to each entity of that type without knowing what it does. The component is notified when the entity is created and after every live change, and it can take over narrow parts of the entity's default behaviour, for instance loading its own models or supplying precise areas to cut out of the terrain. Section~\ref{sec:impl-special} describes the fire type, the one entity type that uses this tier.

\subsection{Layering Rationale}

The three tiers, meaning the table entry, the stateless extension, and the stateful component, form an escalating ladder of specificity. A type uses only what it needs, and most stop at the first tier. Each tier belongs to the type itself and is opt-in; none requires changes to the generic creation, update, or rendering paths. This is the concrete mechanism by which the viewer generalises: the set of supported infrastructure types is data plus a handful of small, isolated extensions, not a concern spread across the application.

\subsection{The Live Update Path}
\label{sec:live-update-path}

Once entities exist, live changes follow a fixed path, shown in Figure~\ref{fig:live-update}. The backend pushes a message over the live-update stream; the update router decodes it into an identifier, a path, and a value, and finds the target entity. The path tells the entity what changed without it having to compare whole records: it may denote a full replacement of the record, a change to one attribute (commonly its position), or a change to one property of a feature.

The entity updates its authoritative data at that path, refreshes its typed copy unless its type opts out for performance, moves itself through the coordinate seam if its coordinates changed, notifies its behaviour component if it has one, and announces the change so that any open information window refreshes.

\section{Geospatial Placement}
\label{sec:geospatial-placement}

Placing content on the Earth at real-world scale is handled through Cesium for Unreal~\cite{cesiumforunreal}, which provides a full WGS84 globe inside the engine and streams terrain and imagery indexed by the 3D~Tiles standard~\cite{ogc3dtiles} (Section~\ref{sec:geospatial-vis}). Rather than letting every entity work with the globe's georeference directly, all conversion from geographic coordinates (latitude, longitude, altitude) to positions in the scene goes through a single coordinate-conversion service, which performs the WGS84~$\rightarrow$~ECEF step itself and delegates the final ECEF~$\rightarrow$~scene step to the globe (both coordinate systems are introduced in Section~\ref{sec:geospatial-vis}).

Concentrating the conversion in a single seam has three benefits. First, the transform, and any future change to it such as switching between an ellipsoidal and a local tangent-plane model, is defined in exactly one place. Second, entities depend on a small, stable interface (``give me the scene position for this lat/lon'') instead of the globe plugin's own interface, so the choice of globe plugin is replaceable. Third, the many places that need placement, such as entity creation, live position changes, the entity-placement tool, and camera framing, are guaranteed to agree, because they all use the same conversion. Terrain height sampling is also mediated here. The globe answers height queries asynchronously against the loaded terrain: it returns nothing until the relevant tiles have streamed in at the required level of detail, so a request made the instant an entity is created can legitimately have no answer yet. Routing every height query through this one seam means every caller, from initial placement to live position changes and the entity-placement tool, handles ``height not yet known'' the same way, typically by deferring placement briefly and asking again, rather than each caller inventing its own fallback.

\section{Design Rationale}
\label{sec:design-rationale}

The architecture rests on a single principle applied at two boundaries: separate what varies from what stays the same, and give each axis of variation exactly one seam.

The data backend varies: credentials, protocol, authentication scheme, pagination, the format of live updates. The service layer contains all of it, behind interfaces expressed in the application's own terms (a record, an update to a path, a position). No rendering, interaction, or camera code names the backend or its formats. The backend can therefore be replaced, or stubbed for offline development and testing, without the rest of the application being aware.

The infrastructure domain varies: what an entity is, how it looks, what it means to select it, how it behaves over time. All of it is contained behind the entity model's registration table and its two extension points. The creation pipeline, live-update loop, selection system, and renderer are written once against a single generic entity.

This is precisely the separation the systems surveyed in Chapter~\ref{chap:state-of-the-art} lack: in those, rendering and interaction code is written against one backend's data model, one fixed set of entity types, or both, so neither can change without changing the viewer's core. Here, both are replaceable seams. Chapter~\ref{chap:implementation} describes how each seam is implemented and the concrete requirements it serves.
