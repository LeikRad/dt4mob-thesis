\chapter{Architecture}
\label{chap:architecture}

\begin{introduction}
This chapter presents the high-level architecture of the digital twin viewer, focusing on the design choices that make it generalizable across infrastructure types and decoupled from any single data backend. It describes the layers the application is divided into, the boundaries between them, and the specific seams through which new entity types are added and the data source is replaced. The concrete decisions taken to arrive at this structure are the subject of Chapter~\ref{chap:implementation}.
\end{introduction}

\section{Overview}
\label{sec:arch-overview}

The viewer is structured as four layers with deliberately narrow interfaces between them, shown in Figure~\ref{fig:arch-overview}:

\begin{itemize}
    \item a \textbf{service layer} of engine-managed singletons that owns all contact with the outside world -- authentication, HTTP requests to the data backend, the live event stream, secure credential storage, remote model downloads, and coordinate conversion;
    \item an \textbf{entity model} that turns a backend record into a world actor, driven by a single registration table and two optional extension points rather than by per-type code scattered through the application;
    \item a \textbf{geospatial placement} seam that is the only place geographic coordinates are turned into engine world positions;
    \item a \textbf{camera, interaction, and UI layer} that operates on actors and on the globe, and has no knowledge of entity types or of where their data came from.
\end{itemize}

The guiding rule is that knowledge of the data backend lives only in the service layer, and knowledge of specific infrastructure domains lives only behind the entity model's extension points. Everything else -- rendering, selection, the camera, the coordinate math, the tile-streaming loop -- is written against generic abstractions (an actor, a \textit{thing} identifier, a latitude/longitude pair) and does not change when a new entity type is added or the backend is swapped.

\section{Service Layer}
\label{sec:service-layer}

Every external dependency is encapsulated in an Unreal Engine \texttt{GameInstanceSubsystem} -- a singleton that the engine creates automatically, keeps alive across level loads, and exposes to the rest of the application through a typed interface. Splitting these responsibilities across small single-purpose subsystems, rather than a single monolithic client, means each concern can be reasoned about, replaced, or mocked in isolation.

\subsection{The Subsystems}

\begin{description}
    \item[\texttt{UDittoService}] The REST client for the data backend. It handles authentication (OAuth2 password grant against a Keycloak endpoint, with HTTP Basic as a fallback), proactive token refresh, and paginated retrieval of \textit{things} (200 per page), including tile-scoped queries expressed as quadkey ranges. API calls issued before authentication completes are queued and flushed automatically once a token is available, so the rest of the application never has to reason about login timing.
    \item[\texttt{UWSService}] The lifecycle of the single persistent WebSocket used for live updates. It defers connecting until \texttt{UDittoService} signals that authentication is ready, sends the backend's stream-start message on connect, and reconnects with exponential back-off (up to a fixed retry count) when the connection drops unexpectedly. Consumers subscribe to connected/message/error/closed delegates instead of touching the socket.
    \item[\texttt{UEntityUpdateDaemon}] The router between the raw event stream and the world. It parses each backend envelope into a \texttt{(thingId, path, value)} triple and dispatches it to the actor registered for that \texttt{thingId}. Events for a \texttt{thingId} with no registered actor are raised on a separate delegate, letting the streaming layer decide whether to fetch and spawn that entity on demand.
    \item[\texttt{UActorRegistryService}] A global \texttt{thingId}~$\rightarrow$~actor map. Actors add themselves on \texttt{BeginPlay} and remove themselves on \texttt{EndPlay}; every system that needs to locate an actor by identifier -- the update daemon, the UI, the tile-refresh logic -- queries this service instead of iterating world actors. It also supports prefix queries, used for example to find an instrument's child entities.
    \item[\texttt{UCredentialStoreService}] Persistence of login credentials through a platform-specific secure-storage backend (Windows DPAPI or macOS Keychain Services). Only the host, username, and password are stored; short-lived OAuth tokens are deliberately not persisted and are re-derived on each launch, which is what lets a session remain valid until the user explicitly logs out. On a platform with no backend implemented, loading simply fails and the login screen is shown every launch.
    \item[\texttt{UGlbModelService}] Downloading, on-disk caching (keyed by HTTP ETag), and runtime parsing of glTF binary models referenced by entities, including splitting a multi-mesh model into individually addressable named layers.
    \item[\texttt{UCoordinatesConversionService}] Geographic-to-world coordinate conversion, described in Section~\ref{sec:geospatial-placement}.
\end{description}

\subsection{Communication Between Subsystems}

The subsystems communicate with each other through delegates rather than direct calls where timing matters. \texttt{UWSService} listens for \texttt{UDittoService}'s ``authentication ready'' broadcast rather than polling it; \texttt{UEntityUpdateDaemon} subscribes to \texttt{UWSService}'s message delegate. Connection settings that more than one subsystem needs (host, protocol, the stream-start message) are read from \texttt{UDittoService}'s getters by the others, so there is a single interpretation of that configuration in the running application rather than each subsystem parsing it independently and potentially drifting.

\subsection{The Backend Boundary}

Nothing above the service layer names an HTTP verb, a URL, an OAuth scope, a WebSocket frame, or the backend's envelope format. The entity model receives parsed JSON objects and \texttt{(thingId, path, value)} triples; the camera and UI receive actors and delegate broadcasts. Replacing the backend, or substituting a mock that replays recorded traffic for offline development, is therefore a change confined to this layer.

\section{Entity Model and Generalization}
\label{sec:entity-model}

The entity model is where generalization across infrastructure types is concentrated. A backend \textit{thing} is a JSON document with an identifier, a set of attributes, and optionally a set of features; the viewer's job is to turn each one into an actor in the world that renders sensibly, shows the right information when selected, and updates live. The design goal is that adding a new kind of infrastructure requires touching exactly one table and, at most, adding one small self-contained class, never modifying the spawn pipeline, the update loop, or the rendering code.

At the time of writing, roughly thirty entity types are registered -- vehicles, weather stations, toll plazas and toll cameras, several classes of road marking, lighting, signs, gantries, kilometre markers, drainage, retaining structures, bridges, four kinds of telematics equipment, generic geo-assets and their instruments, and fire ignition points. All but one are handled without any bespoke rendering or update code.

\subsection{The World Actor}

Every entity is represented by a single actor class, \texttt{ATempUIActor}, regardless of type. On spawn it is initialised with a schema (an Unreal \texttt{USTRUCT} describing the expected JSON shape) and the raw JSON payload. The raw JSON is kept as the authoritative state; a reflected struct instance is kept in sync with it for convenient typed access. The actor carries a Cesium globe-anchor component that pins it to its geographic position through the engine's origin rebasing, a collision volume for cursor hover, and a mesh. It registers with \texttt{UEntityUpdateDaemon} to receive live patches and with \texttt{UActorRegistryService} so it can be found by identifier. Interaction state (hover, selection) is reflected onto every primitive component through custom depth-stencil values, driven by the selection subsystem's delegates.

Crucially, this actor has no per-type branching. It does not know what a toll camera or a weather station is. Everything type-specific reaches it through the mechanisms below.

\subsection{The Registration Table}

There is one function, \texttt{RegisterAllEntityTypes}, that is the single point of contact for adding an entity type. Each call registers a type key (a substring matched against the \texttt{thingId}), the \texttt{USTRUCT} schema for its JSON, a display name for the type picker, a flag for whether the backend has server-side handling for it, an optional default mesh, and an optional extension class. Listing~\ref{lst:register} shows a representative slice.

\begin{lstlisting}[style=cpp,float=t,caption={[The entity-type registration table]A representative slice of \texttt{RegisterAllEntityTypes}. The table is the one place to touch when adding a type, and is kept in its own translation unit so that adding a type does not pull every entity's headers into the factory's compilation.},label={lst:register}]
void RegisterAllEntityTypes(UDT4MOBEntityFactory& Factory)
{
    Factory.RegisterType("meteo", FMeteorologyData::StaticStruct(),
                         TEXT("Meteo Station"), true, FString(),
                         UMeteoExtension::StaticClass());
    Factory.RegisterType("traci", FCarData::StaticStruct(),
                         TEXT("Vehicle"), true, FString(),
                         UVehicleExtension::StaticClass());
    Factory.RegisterType("tolls:toll", FTollData::StaticStruct(),
                         TEXT("Toll Plaza"), true, FString(),
                         UTollExtension::StaticClass());
    // ".instrument." is more specific than "geo-asset" and wins via longest-match
    Factory.RegisterType(".instrument.", FGeoInstrumentData::StaticStruct(),
                         TEXT("Geo Instrument"), true, FString(),
                         UGeoInstrumentExtension::StaticClass());
    Factory.RegisterType("fire:", FIgnitionPointData::StaticStruct(),
                         TEXT("Ignition Point"), false, FString(),
                         UIgnitionPointExtension::StaticClass());
    // ... ~25 more types
}
\end{lstlisting}

At runtime, \texttt{UDT4MOBEntityFactory} matches an incoming \texttt{thingId} against the registered keys -- longest match wins, so a more specific key such as \texttt{.instrument.} takes precedence over a broader \texttt{geo-asset} -- selects the corresponding schema, and spawns an \texttt{ATempUIActor}. A \texttt{thingId} that matches no key is written to a log file for later inspection and otherwise ignored, so an unrecognised entity is a diagnostic event, not a crash or a silent drop with no trace.

\subsection{Stateless Per-Type Behaviour: Extensions}

Most types are fully described by their table entry. When a type needs behaviour the table cannot express, it registers a subclass of \texttt{UEntityTypeExtension} -- a single shared instance per type, with a default implementation of every hook that matches the generic pipeline's fallback. The hooks cover:

\begin{itemize}
  \item the badge colour and label used in outline rows and entity windows;
  \item the default set of info-panel fields;
  \item the JSON body to PUT to the backend when the user places a new instance of the type;
  \item whether the type should be fetched in full rather than by tile, and with what filter;
  \item whether to monitor live-update cadence and warn on stalls;
  \item a per-entity staleness timeout, replacing the backend's shared expiry timestamp;
  \item whether the reflected struct needs re-syncing on every live patch, or only once at initialisation;
  \item whether an actor of this type may be spawned on demand from a live event rather than only by a tile fetch;
  \item an optional behaviour-component class (below).
\end{itemize}

Listing~\ref{lst:vehicleext} shows the vehicle type's extension, which overrides five of these. The factory always returns a valid extension -- a shared generic default for types that registered none -- so callers never branch on ``does this type have custom behaviour''.

\begin{lstlisting}[style=cpp,float=t,caption={[The vehicle type's extension]\texttt{UVehicleExtension}. Each override is a self-contained policy decision for one type, colocated in that type's directory; none of it appears in the generic spawn or update code.},label={lst:vehicleext}]
UCLASS()
class DT4MOB_API UVehicleExtension : public UEntityTypeExtension
{
    GENERATED_BODY()
public:
    virtual TArray<FInfoField> GetDefaultInfoFields() const override;
    virtual FLinearColor GetBadgeColor() const override;
    virtual FString GetBadgeLabel(const FString& TypeKey) const override;

    virtual bool ShouldMonitorUpdateCadence() const override { return true; }

    // Position is read straight from RawJson; skip the per-message reflection walk.
    virtual bool NeedsStructSyncOnLiveUpdate() const override { return false; }

    // TRACI stamps every vehicle in a run with one shared expiry_ts; use a
    // per-vehicle staleness timeout instead so the fleet does not vanish at once.
    virtual float LiveStalenessTimeoutSeconds() const override { return 60.f; }

    // New vehicles can appear while the camera sits still, so the live event
    // is the only channel that catches them.
    virtual bool AllowsOnDemandSpawnFromWS() const override { return true; }
};
\end{lstlisting}

\subsection{Stateful Per-Instance Behaviour: Behaviour Components}

Some types need live per-\textit{instance} state -- fetched GeoJSON geometry, resolved model URLs, a parsed vertex list, a simulation's current exclusion area. A shared extension cannot hold that. For these, the extension returns a \texttt{UEntityBehaviorComponent} subclass, and \texttt{ATempUIActor} attaches one instance of it to each actor of that type, generically -- the actor still has no idea what the component does. The component receives lifecycle callbacks after initialisation and after every live data change, and can override narrow points of the actor's default behaviour (for instance, taking over model loading, or supplying precise terrain-exclusion polygons instead of the default convex hull of the mesh). Chapter~\ref{chap:implementation}, Section~\ref{sec:impl-special}, walks through the one type that uses this rung.

\subsection{Why This Layering}

The three tiers -- table entry, stateless extension, stateful component -- form an escalating ladder of specificity. A type uses only as much of it as it needs, and the large majority stop at the first rung. Every rung lives in the type's own directory and is opt-in; none of them require edits to the generic spawn, update, or render paths. This is the concrete mechanism by which the viewer generalises: the set of supported infrastructure types is data plus a handful of small isolated classes, not a cross-cutting concern.

\subsection{The Live Update Path}
\label{sec:live-update-path}

Once actors exist, live updates flow through a fixed path, shown in Figure~\ref{fig:live-update}. The backend sends a Ditto envelope over the WebSocket; \texttt{UEntityUpdateDaemon} parses it into a \texttt{thingId}, a \texttt{path}, and a value, and looks up the target actor. The \texttt{path} is passed through verbatim and tells the actor what changed without it having to diff JSON:

\begin{itemize}
  \item \texttt{path = "/"} -- a full replacement of the thing object;
  \item \texttt{path = "/attributes/\ldots"} -- a change to an attribute subtree, commonly the position;
  \item \texttt{path = "/features/<name>/properties/\ldots"} -- a change to one feature property.
\end{itemize}

The actor patches its authoritative raw JSON at that path, optionally re-syncs the reflected struct (unless the type opts out for performance), updates its world position through the coordinate seam if the coordinates changed, notifies any behaviour component, and broadcasts a data-changed delegate that the UI binds to.

\section{Geospatial Placement}
\label{sec:geospatial-placement}

Placing content on the Earth at real-world scale is handled through Cesium for Unreal~\cite{cesiumforunreal}, which provides a full WGS84 globe inside the engine and streams terrain and imagery indexed by the 3D~Tiles standard~\cite{ogc3dtiles} (Section~\ref{sec:geospatial-vis}). Rather than let every actor call into Cesium's georeference directly, all conversion from geographic coordinates (latitude, longitude, altitude) to engine world positions goes through one service, \texttt{UCoordinatesConversionService}, which performs the WGS84~$\rightarrow$~ECEF step itself and delegates the final ECEF~$\rightarrow$~world step to the scene's \texttt{CesiumGeoreference}.

Concentrating the conversion in a single seam has three benefits. First, the transform -- and any future change to it, such as switching between an ellipsoidal and a local tangent-plane model -- is defined in exactly one place. Second, actors depend on a small stable interface (``give me the world position for this lat/lon'') instead of on Cesium's API surface, so the choice of globe plugin is itself replaceable. Third, the many call sites that need placement -- initial spawn, live position patches, the entity-placement tool, camera framing -- are guaranteed to agree, because they all call the same function. Terrain height sampling, which the engine performs asynchronously and which returns nothing until the relevant tiles have streamed in, is also mediated here so that callers handle ``height not yet known'' uniformly.

\section{Design Rationale}
\label{sec:design-rationale}

The architecture rests on a single principle applied at two boundaries: \textit{separate what varies from what stays the same, and give each axis of variation exactly one seam}.

The data backend varies -- credentials, wire protocol, authentication scheme, pagination, the live-event envelope format. All of it is contained in the service layer, behind subsystem interfaces expressed in the application's own terms (a \textit{thing}, an update to a path, a world position). No rendering, interaction, or camera code names the backend or its formats. The backend can therefore be replaced, or stubbed for offline development and testing, without the rest of the application being aware.

The infrastructure domain varies -- what an entity is, how it looks, what it means to select it, how it behaves over time. All of it is contained behind the entity model's registration table and its two extension points. The spawn pipeline, the live-update loop, the selection system, and the renderer are written once against a single actor abstraction.

This is precisely the separation the systems surveyed in Chapter~\ref{chap:state-of-the-art} lack: in those, rendering and interaction code is written against one backend's data model, one fixed set of entity types, or both, so neither can change without changing the viewer's core. Here, both are replaceable seams. Chapter~\ref{chap:implementation} traces, through the decisions taken during development, how each seam came to be and what problems motivated it.
