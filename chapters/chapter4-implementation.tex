\chapter{Implementation}
\label{chap:implementation}

\begin{introduction}
This chapter describes how the architecture presented in Chapter~\ref{chap:architecture} is implemented, focusing on the parts of the implementation that show its generalisation and decoupling in practice. Each section covers one concern, describes how the viewer handles it, and relates that solution to the seam it belongs to.
\end{introduction}

\section{Overview}
\label{sec:impl-overview}

The viewer is implemented in Unreal Engine, with the globe provided by Cesium for Unreal. The structure described in Chapter~\ref{chap:architecture}, namely the service layer, the registration table, the two extension points, and the coordinate seam, maps onto a small number of concrete mechanisms in the code. Each exists to meet a specific requirement: keeping credentials and connection details out of source code, streaming a dataset of arbitrary geographic extent, expiring simulated vehicles individually, and accommodating an entity type whose behaviour a table entry alone cannot express.

The components of Chapter~\ref{chap:architecture} are implemented as engine-managed services that live for the whole session. The main ones are the backend connection (\texttt{UBackend\-Connection\-Service}), the live-update stream (\texttt{UWSService}), the update router (\texttt{UEntityUpdateDaemon}), and the generic entity (\texttt{ATempUIActor}); the rest of this chapter refers to them by role.

Section~\ref{sec:impl-backend} covers how backend specifics are kept out of the application's code. Section~\ref{sec:impl-streaming} covers streaming entities by geographic area and the measures that keep it reliable. Section~\ref{sec:impl-worked-example} walks through adding a new entity type end to end. Section~\ref{sec:impl-camera} covers the camera and interaction layer and why it is unaffected by changes on the entity side. Section~\ref{sec:impl-special} covers the one place genuinely domain-specific behaviour lives, and how it stays behind the same seam as every other type. Section~\ref{sec:impl-discussion} reflects on which parts of the design generalise well and which introduce complexity.

\section{Decoupling the Data Backend}
\label{sec:impl-backend}

Backend knowledge is kept out of the application's code in three complementary ways: connection settings are structured configuration data, credentials are runtime state, and the backend's protocol details sit behind a set of explicit interfaces. The subsections below cover each in turn, followed by what replacing the backend would still require.

\subsection{Configuration and Credentials as Structured Runtime Data}
\label{sec:impl-dataasset}

Connection settings and credentials are never embedded in source code, and no service parses them from text on its own. Non-secret connection defaults (host, protocol, OAuth client identifier, and the message that starts the event stream) live in a single configuration asset, an engine object edited in the editor and loaded exactly once, when the backend connection starts. There is therefore a single load point and a single structured representation of the configuration, which no two services can interpret differently.

Real per-user credentials do not live in that asset at all. The user enters them at runtime on a dedicated login screen, and the backend connection performs an OAuth2 password grant against a Keycloak identity server; starting the service never authenticates on its own. As a result, authentication is asynchronous relative to the rest of startup, and several components need the result. This is coordinated entirely through events and a request queue, shown in Figure~\ref{fig:auth-sequence}: any request issued before a token arrives is queued by the backend connection and sent automatically once it does, and the live-update stream does not open its connection until the backend connection announces that authentication is ready. No caller has to reason about login timing; it gets either an immediate result or one that arrives slightly later.

A separate credential store keeps the login details in platform secure storage (Windows DPAPI or macOS Keychain Services). Only the host, username, and password are stored; the short-lived OAuth access and refresh tokens are deliberately never written to disk. Instead, a fresh password grant is performed on every launch. This is a deliberate trade: it avoids the failure mode where a stored refresh token silently goes stale between sessions, at the cost of one extra round-trip at startup, and it means a stored login stays usable until the user explicitly logs out. On a platform with no secure-storage support implemented, loading fails and the login screen is shown on every launch, a graceful degradation rather than an error.

The login flow is also isolated in the scene itself: it runs in its own minimal level with no camera, no world geometry, and no globe, so none of the streaming machinery starts before the user is authenticated.

\subsection{A Single Source of Truth for Connection Settings}

With settings loaded once by the backend connection, the other services that need them read them from it rather than loading the configuration a second time; the live-update stream, in particular, takes its host, protocol, and stream-start message this way. The result is one interpretation of the connection configuration in the running application, and one moment when the live connection is considered ready, rather than each service arriving at its own.

\subsection{An Interface Behind the Backend Contact}
\label{sec:impl-backend-interface}

Backend-specific detail lives only in the backend connection, the live-update stream, and the message decoding of the update router (Section~\ref{sec:service-layer}). Within those three, it sits behind three small interfaces, one per genuinely backend-specific responsibility, so that a second implementation can be written against them. Each currently has exactly one implementation, for Eclipse Ditto.

The REST client interface (\texttt{IBackendRestClient}) covers authentication and access to the backend's records. The backend connection holds one Ditto implementation and forwards its operations, such as logging in, fetching records, and creating a record, to it; the Keycloak token exchange and Ditto's API addresses all live in that implementation. The event subscription interface (\texttt{IBackendEventSubscription}) covers the live connection's protocol: its address, its subprotocol, and the commands that start and stop the event stream. Almost none of the live-update stream is backend-specific, since reconnection, event broadcasting, and sending messages do not vary by backend and stay in the stream itself, so this interface covers only those few protocol details. Finally, the envelope parser interface (\texttt{IBackendEnvelopeParser}) decodes one live-update message into the generic \emph{(identifier, path, value)} triple that the update router routes on. It is the only backend-specific part of the update router (Section~\ref{sec:live-update-path}), and a parser for a different message format can replace it.

Each service keeps its own public operations, events, and lifecycle, and owns its interface implementation the same way the entity model owns extensions and behaviour components: created once, held through a generic interface, with the owner unaware of what the owned object actually does (Section~\ref{sec:entity-model}). Callers use only the service's own operations and never see the interface. This is the same composition pattern applied to a second axis of variation, not a new idea introduced for the backend specifically.

\subsection{What Backend Replacement Would Still Require}
\label{sec:impl-replace-caveat}

Because backend-specific detail sits behind the three interfaces above, a backend change means writing one implementation of each and creating it at startup instead of the Ditto one, not rewriting the backend connection, the live-update stream, or the update router. What does \emph{not} yet exist is a second implementation, an offline mock behind the same interfaces, or a runtime or configuration switch between implementations; the Ditto implementation is currently selected directly in the code. This is the same bounded, one-place scope of change that each new entity type needs at the entity-schema level, applied here to the connection itself. Chapter~\ref{chap:conclusions} revisits this alongside the other research questions.

\section{Entity Streaming and Reliability}
\label{sec:impl-streaming}

\subsection{Streaming Entities by Geographic Area}

Loading every entity in the dataset regardless of where the camera is looking does not scale, and baking in an assumption about dataset size would undermine the goal of generalising across infrastructure of arbitrary extent. Instead, the streaming loop maps the camera's altitude to a discrete zoom level and, above a threshold zoom, fetches only the entities within the 3$\times$3 grid of map tiles around the camera, requested from the backend as ranges of tile keys. Below the threshold zoom, tile filtering is disabled and everything loads, since at that range the whole area of interest is on screen anyway. Figure~\ref{fig:tile-flow} shows the decision path taken at each check.

  \label{fig:tile-flow}
\end{figure}

Keeping this stable under a continuously moving camera takes several guards, each addressing a specific failure mode. A periodic check, every ${\sim}0.5$\,s rather than every frame, detects when the camera has entered a new tile. A debounce then delays the actual refresh until the camera has held still for ${\sim}0.75$\,s, so sweeping the view across several tiles issues one refresh, not one per tile crossed, and the refresh itself only removes and re-fetches the tiles that actually changed, keeping the ones still in view. Zoom changes need a guard of their own: the zoom level is derived from the camera's altitude by rounding, so an altitude sitting exactly on a zoom boundary would flip between two levels on tiny camera movements, and every flip would rebuild the entire scene. A zoom-change hold therefore requires a new zoom level to persist for ${\sim}2$\,s before it is committed. Finally, entities that are still in view or have an open information window when their tile unloads are kept alive as ``orphans'' and removed later, once they are neither, rather than disappearing from under the user.

The live event subscription is scoped to match the tile filter: when zoomed out past the tile-filtering threshold, individual simulated vehicles are smaller than a pixel and their high-frequency updates would dominate the live connection for no visible benefit, so the subscription excludes them entirely at that range, even though the tile filter itself is dropped.

\subsection{Per-Entity Expiry for Simulated Fleets}
\label{sec:impl-ttl}

Ephemeral entities, such as simulated vehicles, carry an expiry timestamp set by the backend. A group of entities updated at the same time can end up with the same expiry timestamp. The viewer does not remove vehicles by that timestamp directly, because its copy is only as recent as the last message it received: a vehicle that is still active but whose latest update simply arrives late would look expired and be removed. The generic path has no way to express this, so it is handled through the stateless extension point: the vehicle type's extension sets a per-entity staleness timeout (60\,s), so an entity is removed only when no update for that specific entity has arrived within that window, with the timer reset on every message it receives. Vehicles that really stopped updating are removed; vehicles still active, or merely running behind on messages, are not. The same extension also tells the entity not to refresh its typed copy of the data on every message, since a vehicle's position is read directly from its raw data and a full refresh per message would be pure overhead at that update frequency.

\section{Adding an Entity Type: A Worked Example}
\label{sec:impl-worked-example}

To make the generalisation concrete, consider adding a hypothetical new infrastructure type, an air-quality sensor whose identifier contains \texttt{air-quality} and whose attributes hold the current readings. The full set of changes takes two or three steps. The first is to declare a data schema mirroring the sensor's JSON: its latitude, longitude, and the readings. The engine's JSON conversion fills it in from that declaration alone. The second is to add one entry to the registration table, associating the key \texttt{air-quality} with that schema and the display name ``Air Quality Sensor''. The third step is optional: if the default grey badge and empty information panel are not wanted, an extension for the type sets its badge colour, badge label, and default information fields.

Nothing else changes. The entity factory now creates a generic entity for any matching identifier; the streaming loop fetches it like any other entity; the update router delivers its live updates; the entity updates its data, moves through the coordinate seam, and refreshes the UI; selection, hover, and both camera modes work unmodified. No changes are required to the creation pipeline, the update loop, the renderer, or the camera. This three-step (often two-step) process is the operational meaning of the generalisation claim in RQ1.

\section{Camera and Interaction}
\label{sec:impl-camera}

The camera is a single controller with two modes. In the overhead (RTS) mode, it looks straight down from a distance that sets the zoom, ranging from roughly $1.5$\,km to planetary distance, and re-aligns itself every frame so that the view stays oriented to local north and east on the globe. In the free-fly mode, it moves freely in all six degrees of freedom, staying upright relative to the globe surface. Both modes compute their alignment from the globe's local north and up directions at the camera's position.

The key point about the camera is what it does \emph{not} reference. It queries the globe for orientation, and it operates on entities and on the cursor for interaction. It knows nothing about entity types, the backend, or the data model. Selection and hover are likewise generic: a selection manager announces hover and selection changes, and the generic entity responds by highlighting its meshes, with no per-type branching; the on-screen interface listens to the same announcements to show or hide the entity's information window. As a result, the camera and interaction layer is unaffected by changes on the entity side: adding, removing, or reworking an entity type never touches it.

\section{Special-Case Handling}
\label{sec:impl-special}

Fire-simulation entities are the one place genuinely infrastructure-specific behaviour exists in the viewer. A fire entity loads two separate 3D models (a spread cone and a simulation body), fetches and parses the fire's perimeter geometry, and cuts precise areas out of the terrain so that the burned area reads correctly against it.

None of this could be expressed through a table entry or a stateless extension, because it involves live per-instance state: fetched geometry, resolved model locations, parsed polygon outlines. It is therefore implemented as a behaviour component, provided by the fire type's extension and attached by the generic entity to each fire entity when it is created. The entity does not know what the component does; it only knows that some types supply one. The component takes over the two narrow points it needs: it loads its own models, and it supplies exact terrain cut-out areas in place of the entity's default behaviour of deriving one from the outline of its visible model.

Both keep fire-specific behaviour behind the same seam every other type uses, as sketched in Figure~\ref{fig:fire-fix}. Because the component loads its own models, the generic model-loading path contains no fire-specific branch; the staged loading of the cone and simulation models happens entirely inside the component. The cut-out areas are returned as a \emph{map} of named polygons (the cone and the simulation), and the generic entity creates one terrain cut-out per entry. The entity only iterates the map and does not know what each polygon represents, so the cone and the simulation area can be shown at the same time without any fire-specific code in the entity, the factory, or the update loop.

\section{Discussion}
\label{sec:impl-discussion}

Some parts of this design generalise cleanly, and some introduce complexity worth naming.

The registration table plus the two extension mechanisms hold up well. Roughly thirty entity types are currently registered: vehicles, weather stations, toll plazas and toll cameras, several classes of road marking, lighting, signs, gantries, kilometre markers, drainage, retaining structures, bridges, four kinds of telematics equipment, generic geo-assets and their instruments, and fire ignition points. All of them fit one of the model's three tiers, and none of them requires a change to the generic creation, update, or rendering paths; the worked example in Section~\ref{sec:impl-worked-example} is the normal case. The fire component, the most demanding entity in the system and the only one with bespoke rendering or update code, fits the stateful-component tier without forcing an exception. The coordinate-conversion seam and the configuration-as-data approach are similarly low-cost, the latter because a single structured configuration leaves no room for two services to interpret the connection settings differently.

Backend independence, discussed in full in Sections~\ref{sec:impl-backend-interface} and~\ref{sec:impl-replace-caveat}, rests on an actual interface rather than only on inspection: three small interfaces isolate authentication and record access, the live-connection protocol, and the message format, each with one implementation. What remains is a second implementation to plug into them, or an offline mock; writing either would not, on its own, make a different backend's data usable without also conforming to its schema, the same work every new entity type already requires. What the seam buys either way is that a backend change stays a bounded rewrite behind a fixed contract instead of spreading through the application.

The tile-streaming loop is where complexity concentrates. Each of its guards, meaning the debounce, the changed-tiles-only refresh, the zoom-change hold, and the orphan sweep, addresses a specific failure mode. Still, together they make that loop the most intricate part of the codebase.

This sets up the evaluation in Chapter~\ref{chap:evaluation}. The performance benchmarks target the entity creation and rendering path, exercised most heavily by high-cardinality types such as signs and simulated vehicles, to establish both how that path scales with entity count and which mesh and material strategy such a type should adopt to balance rendering cost against the disk space and hosting cost of storing many visually distinct models (RQ3); the per-type indirection itself (one lookup for the extension and one for the schema, per entity created) is negligible by inspection and is not separately measured. The user testing targets the camera and interaction layer, since the question there is whether a layer built to be generic over the data still feels coherent to someone using it to explore a specific dataset, and whether the partner use cases of Section~\ref{sec:usecases} are not just architecturally accommodated (Section~\ref{sec:eval-usecases}) but usable in practice by someone unfamiliar with the underlying data model (RQ4).
