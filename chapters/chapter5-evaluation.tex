\chapter{Evaluation}
\label{chap:evaluation}

\begin{introduction}
This chapter evaluates the viewer along the two axes set out in Chapter~\ref{chap:introduction}: the performance and scaling of the entity spawning and rendering path (RQ3), assessed with a dedicated benchmark harness, and the usability and coherence of the application for its intended users (RQ4), assessed through a user study. The chapter states the design and methodology of each in full; results are reported as they become available.
\end{introduction}

\section{Evaluation Overview}
\label{sec:eval-overview}

The two research questions call for different methods. RQ3 is quantitative and controlled: it asks how spawn time, memory, and frame cost grow as the number of rendered entities increases, and how that growth differs between rendering strategies for a high-cardinality entity type. It is answered with a synthetic benchmark that spawns entities in known quantities under each strategy and records engine-level metrics, isolated from the live backend and from user input. RQ4 is qualitative and situated: it asks whether a person unfamiliar with the underlying data model can use the viewer to accomplish realistic tasks. It is answered with a moderated user study using the real application against a real dataset.

\section{Performance Benchmarks}
\label{sec:eval-benchmarks}

\subsection{Rationale and Subject}

The entity type chosen as the benchmark subject is the road sign. Signs are the clearest case of a high-cardinality type: a real road network contains them in the tens of thousands, they share a small number of base geometries (circular and triangular blanks) but differ in their face texture, and they are all rendered with the same simple flat-panel material. This makes them an ideal stress test for the spawning and rendering path and, separately, a clean setting in which to compare mesh and material batching strategies, since the only thing that varies between one sign and another is which texture it shows.

Three strategies are compared, implemented as interchangeable \texttt{USignSpawnStrategy} subclasses:

\begin{description}
    \item[\textsc{PerSign}] The naive baseline. One fully self-contained, pre-baked mesh with its texture baked in per sign code, placed as an individual static mesh component. No instancing. Expected to lose on both draw calls and on-disk/in-memory size because geometry is duplicated per code.
    \item[\textsc{PerTexture}] One shared mesh per base shape, but a separate dynamic material instance and a separate Instanced Static Mesh (ISM) component per distinct sign texture, because the engine cannot batch different materials into one ISM. Instance and geometry count match \textsc{AtlasMaterial}, but there are as many components, materials, and draw calls as there are distinct textures.
    \item[\textsc{AtlasMaterial}] One shared mesh and one shared atlas-textured material per base shape, with every instance of that shape batched into a single ISM. Each instance carries four floats of per-instance custom data (a UV offset and scale) selecting its cell in the packed atlas texture. Two shapes therefore mean two components, two materials, and two draw calls regardless of how many distinct signs are shown.
\end{description}

\subsection{Harness}

The benchmark is a standalone console-driven harness (\texttt{ASignBenchmarkGameMode}), set as a per-level game-mode override on an otherwise empty level and deliberately kept entirely separate from the Ditto entity pipeline -- its own asset-fetching subsystem, its own on-disk cache -- so that it cannot perturb, or be perturbed by, the production code path. A run is triggered by a console command naming a strategy and an instance count; instances are placed on a regular grid, cycling through the 17 available sign codes. Each run destroys and respawns a fresh root actor so no state leaks between measurements.

For each run the harness records:

\begin{itemize}
    \item \textbf{prepare time} -- from the first asset request to all assets ready (download from cache, decode, atlas construction);
    \item \textbf{spawn time} -- from assets-ready to the last instance placed;
    \item \textbf{instance, component, unique-mesh, unique-material, and unique-texture counts} -- the structural cost of the strategy;
    \item \textbf{frame timing} -- steady-state GPU and game-thread frame time with the instances in view, from the engine's own statistics.
\end{itemize}

\subsection{Methodology}
\label{sec:eval-method}

Per supervisor feedback, every metric is captured over ten runs per configuration and averaged, including metrics that are themselves engine-reported averages (such as mean frame time), so that run-to-run variance from background OS activity and shader compilation is smoothed out. The first run after launch for each strategy is treated as a warm-up and discarded to exclude one-off shader compilation and cache-population costs.

\subsection{Objectives}

The study assesses whether the viewer is usable and coherent for its intended users -- people who work with road-infrastructure data but are not familiar with the viewer's internal data model -- when carrying out realistic inspection tasks against a real dataset. The specific questions are whether participants can navigate to a location of interest, locate and identify entities, read an entity's details, and understand what they are seeing, without assistance and without prior training on the tool.

\subsection{Tasks}

Participants carry out a fixed sequence of tasks with the live application, thinking aloud:

\begin{enumerate}
    \item navigate from the initial view to a named road segment (tests camera controls, both modes);
    \item find a specific class of entity in that area -- for example a toll camera or a weather station -- and select it (tests visibility, hover and selection feedback, the entity type filter);
    \item read a named attribute from the selected entity's detail panel (tests the info panel);
    \item identify what a highlighted simulated or special entity represents -- a vehicle, or a fire's spread area (tests whether non-infrastructure entities are legible);
    \item locate an entity by identifier using any means the UI provides.
\end{enumerate}

\subsection{Measures}

\begin{itemize}
    \item \textbf{Task success}, scored as complete / completed with difficulty / failed;
    \item \textbf{Time on task};
    \item \textbf{Errors and points of confusion}, from observation and think-aloud;
    \item \textbf{Perceived usability}, via the System Usability Scale administered after the session;
    \item \textbf{Debrief comments}, from a short semi-structured interview.
\end{itemize}
